# go-evtx v0.7.0 — Format Correctness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make go-evtx-generated `.evtx` files parse in the Windows Event Log stack, and prove it with CI rather than claiming it.

**Architecture:** The two CI verification jobs (F6) are built **first**, against unmodified v0.6.0 output, and their failure is recorded as a baseline. Five on-disk format defects (F1–F5 in the spec) are then fixed in the writer, and the jobs are re-run to settle whether the files parse. Verifying against parsers we do not control — python-evtx on Linux, `Get-WinEvent` on `windows-latest` — is the whole point: the existing Go suite round-trips go-evtx against go-evtx, so a shared misunderstanding of the format is invisible to it. The enabling change for F1 is chunk-scoped tracking of where each NameNode and TemplateNode lands, which lets `flushChunkLocked` populate the two per-chunk hash tables that are currently all zeros.

**Why the verification comes first:** every fix in this plan is a hypothesis about why these files do not open in Event Viewer. Measuring the failure before fixing it turns six blind changes into six changes with a signal — and if the recorded error points somewhere the plan does not go, that is worth knowing on day one rather than at the end.

**Tech Stack:** Go (single package `evtx`, zero external dependencies), GitHub Actions, python-evtx (test-only, via `uvx`), PowerShell `Get-WinEvent`.

**Spec:** `docs/superpowers/specs/2026-08-08-durability-and-format-correctness-design.md`, section "Release 2 — v0.7.0, format correctness".

## Global Constraints

- **Zero external runtime dependencies.** `go.mod` must have no `require` block for anything but the standard library. `golang.org/x/sys` is explicitly forbidden. Test-only tooling that runs in CI (python-evtx via `uvx`) is not a Go dependency and is allowed.
- **Go directive stays at `1.26.5`.** Do not raise or lower it.
- **`go test -race ./... -count=1` must pass.** The writer is concurrent; the race detector is not optional.
- **`GOOS=windows go build ./...` must pass.** The build-tag pair `evtx_unix.go` / `evtx_windows.go` must stay in sync — every symbol defined in one is defined in the other.
- **`golangci-lint run` must report 0 issues.**
- **Unexported helpers whose name ends `Locked` require the caller to hold `w.mu`** and carry a `// CALLER MUST HOLD w.mu.` comment. This is an existing repo convention; new helpers follow it.
- **`rotate()` requires `w.mu` held by the caller and must never acquire it itself.**
- **Records larger than a chunk are rejected, never truncated.** Any change to record sizing must preserve this and update `maxRecordPayload` accordingly.
- **No claim in `README.md` may be restored unless a CI job proves it.** This is the rule the v0.6.0 honesty pass established; v0.7.0 restores claims only as their jobs go green.
- **Do not mix `WriteRecord` and `WriteRaw` in one session.** Existing API contract; unchanged here.

## Background the implementer needs

`.evtx` files are a sequence of 65536-byte chunks after a 4096-byte file header. Each chunk begins with a 512-byte header, then event records from offset 512 (`evtxRecordsStart`).

Two arrays inside every chunk header are currently left entirely zero:

| Range | Contents | Entries |
|---|---|---|
| `[128:384]` | Common-string offset array | 64 × uint32 |
| `[384:512]` | Template offset array | 32 × uint32 |

Each entry is a **chunk-relative** offset to the first node in that bucket, or 0 for an empty bucket. Nodes in the same bucket chain through a `next_offset` field that is the first 4 bytes of both the NameNode and the TemplateNode structures.

python-evtx tolerates the zeros because it follows the inline `template_offset` carried in each record instead of consulting the tables. A parser that resolves through the tables — which Event Viewer is believed to do — finds nothing. That is F1, and it is the reason this release exists.

**Already correct, do not "fix":** `patchChunkCRC` (`binformat.go:111-120`) computes the chunk header checksum over `chunk[0:120]` + `chunk[128:512]` and writes it at `chunk[124:]`. That matches python-evtx's `calculate_header_checksum` exactly. Because the checksummed range already covers both tables, filling them is automatically reflected in the CRC — **provided the tables are written before `patchChunkCRC` is called**. That ordering is the single most important constraint in Task 6.

**Already done in v0.6.0, do not redo:** the spec's F5 says "`flushChunkLocked` increments `w.chunkCount` before patching the header; patch first, then increment." That was fixed during the v0.6.0 durability work — see `evtx.go:604-615`, which computes `nextChunkCount`, patches, syncs, and only then commits. F5 in this plan covers **only** the remaining two parts: the `uint16` overflow guard and the `LastChunkNumber` underflow. Likewise the spec's F7 (README honesty pass) shipped in v0.6.0.

```go
// Command gen-fixture writes a .evtx file and a JSON description of what a
// correct parser must find in it. Both CI verification jobs consume the pair,
// so the expectations cannot drift from the fixture.
package main

import (
	"encoding/json"
	"flag"
	"fmt"
	"os"
	"path/filepath"
	"strings"

	evtx "github.com/fjacquet/go-evtx"
)

type expected struct {
	RecordCount int      `json:"record_count"`
	EventIDs    []int    `json:"event_ids"`
	ObjectNames []string `json:"object_names"`
}

func main() {
	out := flag.String("out", ".", "output directory")
	flag.Parse()

	path := filepath.Join(*out, "generated.evtx")
	w, err := evtx.New(path, evtx.RotationConfig{})
	if err != nil {
		fatal(err)
	}

	var exp expected
	// Enough records to span several chunks, with content a parser can check.
	for i := 0; i < 400; i++ {
		objectName := fmt.Sprintf(`C:\logs\file-%03d.txt`, i)
		switch i % 4 {
		case 1:
			objectName = `C:\journaux\fichier-é-à-ü.txt` // non-ASCII, BMP
		case 2:
			objectName = `C:\logs\emoji-🔥-` + fmt.Sprint(i) // non-BMP, surrogate pair
		case 3:
			objectName = `C:\logs\` + strings.Repeat("w", 2000) // long, but well under the limit
		}
		fields := map[string]string{
			"SubjectUserName": "verifier",
			"ObjectName":      objectName,
			"ObjectType":      "File",
			"TimeCreated":     "2026-08-08T12:00:00Z",
		}
		if err := w.WriteRecord(4663, fields); err != nil {
			fatal(fmt.Errorf("record %d: %w", i, err))
		}
		exp.RecordCount++
		exp.EventIDs = append(exp.EventIDs, 4663)
		exp.ObjectNames = append(exp.ObjectNames, objectName)
	}

	if err := w.Close(); err != nil {
		fatal(err)
	}

	blob, err := json.MarshalIndent(exp, "", "  ")
	if err != nil {
		fatal(err)
	}
	if err := os.WriteFile(filepath.Join(*out, "expected.json"), blob, 0o644); err != nil {
		fatal(err)
	}
	fmt.Printf("wrote %s (%d records)\n", path, exp.RecordCount)
}

func fatal(err error) {
	fmt.Fprintln(os.Stderr, "gen-fixture:", err)
	os.Exit(1)
}
```

- [ ] **Step 2: Write the differential checker**

```python
#!/usr/bin/env python3
"""Parse a go-evtx-generated file with python-evtx and check it against the
generator's own expectations.

This is the differential the v0.6.0 audit found missing: the Go test suite
round-trips go-evtx against go-evtx, so any shared misunderstanding of the
format is invisible. python-evtx is an independent implementation.
"""
import json
import sys
import xml.etree.ElementTree as ET

import Evtx.Evtx as evtx


def main(evtx_path: str, expected_path: str) -> int:
    with open(expected_path) as fh:
        expected = json.load(fh)

    object_names = []
    count = 0
    with evtx.Evtx(evtx_path) as log:
        for record in log.records():
            root = ET.fromstring(record.xml())
            ns = {"e": "http://schemas.microsoft.com/win/2004/08/events/event"}
            for data in root.iterfind(".//e:Data", ns):
                if data.get("Name") == "ObjectName":
                    object_names.append(data.text or "")
            count += 1

    failures = []
    if count != expected["record_count"]:
        failures.append(f"record count: got {count}, want {expected['record_count']}")
    if object_names != expected["object_names"]:
        for i, (got, want) in enumerate(zip(object_names, expected["object_names"])):
            if got != want:
                failures.append(f"record {i} ObjectName: got {got!r}, want {want!r}")
                break
        if len(object_names) != len(expected["object_names"]):
            failures.append(
                f"ObjectName count: got {len(object_names)}, want {len(expected['object_names'])}"
            )

    # Checksums: python-evtx exposes them, and a wrong CRC is exactly the kind
    # of damage a self-round-trip cannot see.
    with evtx.Evtx(evtx_path) as log:
        fh = log.get_file_header()
        for i, chunk in enumerate(fh.chunks()):
            if not chunk.check_magic():
                break
            if chunk.calculate_header_checksum() != chunk.header_checksum():
                failures.append(f"chunk {i}: header checksum mismatch")
            if chunk.calculate_data_checksum() != chunk.data_checksum():
                failures.append(f"chunk {i}: data checksum mismatch")

    if failures:
        print("FAIL")
        for f in failures:
            print("  -", f)
        return 1

    print(f"OK: {count} records, all chunk checksums verify")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

```yaml
  get-winevent:
    needs: generate          # NOT python-evtx-differential — see the note above
    runs-on: windows-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v5
        with: { persist-credentials: false }
      - uses: actions/download-artifact@v5
        with:
          name: generated-evtx
          path: artifacts
      - name: Parse with Get-WinEvent
        shell: pwsh
        run: |
          $ErrorActionPreference = 'Stop'
          $expected = (Get-Content artifacts/expected.json | ConvertFrom-Json)

          # Get-WinEvent returns a scalar for a single record; coerce to an array.
          $events = @(Get-WinEvent -Path artifacts/generated.evtx -ErrorAction Stop)

          if ($events.Count -ne $expected.record_count) {
              throw "record count mismatch: got $($events.Count), want $($expected.record_count)"
          }

          # Count alone proves nothing — a parser returning the right number of
          # empty records would pass. Check content survives the round trip.
          $first = $events[0]
          $xml = [xml]$first.ToXml()
          $objectName = ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'ObjectName' }).'#text'
          if ($objectName -ne $expected.object_names[0]) {
              throw "ObjectName mismatch: got '$objectName', want '$($expected.object_names[0])'"
          }

          Write-Host "OK: $($events.Count) records, ObjectName round-trips"
```

`Get-WinEvent -Path` uses the same Windows Event Log parsing stack as Event Viewer. If it parses, the claim is earned.

**Files:**
- Create: `testdata/system.evtx`
- Create: `testdata/README.md`
- Create: `chunkhash.go`
- Create: `chunkhash_test.go`
- Modify: `binxml.go` (remove `sdbmHash`, lines 369-375)

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces, all in `chunkhash.go` and used by Tasks 2, 3 and 4:
  - `sdbmHash(s string) uint32` — SDBM over UTF-16 code units
  - `guidHash(guid []byte) uint32` — SDBM over a 16-byte GUID read as 8 LE uint16 units
  - `nameBucket(h uint32) int`, `templateBucket(guid []byte) int`
  - `putBucket`/`getBucket` and the `numStringBuckets`/`numTemplateBuckets`/`stringTableStart`/`templateTableStart` constants

**Note on the template rule.** An earlier revision of this plan, following the spec, said templates bucket by `template_id % 32` over the first four GUID bytes. That was never checked before being written down, and it is wrong: measured across two Windows-generated files it scores 10 of 386 real entries, i.e. chance. The corrected rule — SDBM over the full GUID as 8 LE uint16 units — scores 386 of 386. The spec's F1 section carries the measurement table.

- [ ] **Step 3: Write the failing hash-rule test**

Create `chunkhash_test.go`. This reads real chunks and asserts that every populated bucket contains only names whose hash lands in that bucket. It is a **discovery** test as much as a regression test: if the rule is wrong it fails loudly and the plan changes.

```go
// chunkhash_test.go — validates go-evtx's chunk hash table rules against a
// real Windows-generated file. See testdata/README.md for provenance.
package evtx

import (
	"encoding/binary"
	"os"
	"testing"
	"unicode/utf16"
)

// readFixtureChunk returns chunk n of testdata/system.evtx as a 65536-byte
// slice, failing the test if it is absent or not a chunk.
func readFixtureChunk(t *testing.T, n int) []byte {
	t.Helper()
	chunk, ok := readFixtureChunkOK(t, n)
	if !ok {
		t.Fatalf("fixture has no chunk %d", n)
	}
	return chunk
}

// readFixtureChunkOK is readFixtureChunk for callers that walk until the file
// runs out. It reports ok=false past the last chunk instead of failing, and
// still fails hard on a chunk that exists but has bad magic — that would mean
// the fixture is damaged, not that the walk finished.
func readFixtureChunkOK(t *testing.T, n int) ([]byte, bool) {
	t.Helper()

// nameNodeAt decodes a NameNode at a chunk-relative offset.
// Layout: next_offset(4) hash(2) char_count(2) UTF-16LE chars null(2)
func nameNodeAt(t *testing.T, chunk []byte, off uint32) (next uint32, storedHash uint16, name string) {
	t.Helper()
	if int(off)+8 > len(chunk) {
		t.Fatalf("NameNode offset %d out of range", off)
	}
	next = binary.LittleEndian.Uint32(chunk[off:])
	storedHash = binary.LittleEndian.Uint16(chunk[off+4:])
	n := int(binary.LittleEndian.Uint16(chunk[off+6:]))
	u16 := make([]uint16, n)
	for i := 0; i < n; i++ {
		u16[i] = binary.LittleEndian.Uint16(chunk[int(off)+8+2*i:])
	}
	return next, storedHash, string(utf16.Decode(u16))
}
```

Move `sdbmHash` out of `binxml.go` (delete lines 369-375 there) and into the new file. **Change it to hash UTF-16 code units, not UTF-8 bytes.** The existing implementation iterates `[]byte(s)`; the EVTX format hashes the UTF-16 representation. For ASCII the two are numerically identical, so no already-written file changes behaviour — but a non-ASCII element or attribute name would hash wrong today.

```go
// chunkhash.go — the per-chunk common-string and template hash tables.
//
// Every EVTX chunk header carries two offset arrays that a parser uses to find
// names and templates without walking every record:
//
//	[128:384]  64 × uint32  common-string buckets
//	[384:512]  32 × uint32  template buckets
//
// Each entry is a chunk-relative offset to the first node in that bucket, or 0
// if the bucket is empty. Nodes in one bucket chain through a next_offset field
// that is the first 4 bytes of both the NameNode and TemplateNode structures.
//
// go-evtx left both arrays zero through v0.6.0. python-evtx tolerates that
// because it follows each record's inline template_offset instead; a parser
// that resolves through the tables finds nothing.
package evtx

import (
	"encoding/binary"
	"unicode/utf16"
)

// sdbmHash is the EVTX name hash: h = h*65599 + c over the UTF-16 code units
// of the string, expressed as the usual shift form (h<<6 + h<<16 - h).
//
// Hashing UTF-16 code units, not UTF-8 bytes, is what the format requires.
// The two agree for ASCII — every name go-evtx emits today is ASCII — but they
// diverge above U+007F, where UTF-8 contributes several bytes and UTF-16
// contributes one unit with a value above 255.
func sdbmHash(s string) uint32 {
	var h uint32
	for _, c := range utf16.Encode([]rune(s)) {
		h = uint32(c) + (h << 6) + (h << 16) - h
	}
	return h
}

// nameBucket maps a name hash to one of the 64 common-string buckets.
//
// Only the low 16 bits of the hash are stored in a NameNode, but 64 divides
// 65536, so bucketing the truncated hash and the full hash give the same
// answer. Callers may pass either.
func nameBucket(h uint32) int { return int(h % numStringBuckets) }

// guidHash is the template equivalent of sdbmHash: the same SDBM routine, fed
// the full 16-byte GUID read as 8 little-endian uint16 units.
//
// Windows hashes 16-bit units, and a GUID is simply eight of them — the
// template rule is the general rule, not a special case. Hashing only the
// first four bytes as a uint32 "template_id", or hashing the 16 bytes
// individually, both fail against real files; see the measurement table in the
// spec's F1 section.
func guidHash(guid []byte) uint32 {
	var h uint32
	for i := 0; i+1 < len(guid); i += 2 {
		c := uint32(guid[i]) | uint32(guid[i+1])<<8
		h = c + (h << 6) + (h << 16) - h
	}
	return h
}

// templateBucket maps a template GUID to one of the 32 template buckets.
func templateBucket(guid []byte) int { return int(guidHash(guid) % numTemplateBuckets) }

const (
	numStringBuckets   = 64
	numTemplateBuckets = 32

	stringTableStart   = 128 // chunk[128:384]
	templateTableStart = 384 // chunk[384:512]
)

// putBucket writes a chunk-relative offset into bucket i of the array starting
// at tableStart.
func putBucket(chunk []byte, tableStart, i int, off uint32) {
	binary.LittleEndian.PutUint32(chunk[tableStart+i*4:], off)
}

// getBucket reads bucket i of the array starting at tableStart.
func getBucket(chunk []byte, tableStart, i int) uint32 {
	return binary.LittleEndian.Uint32(chunk[tableStart+i*4:])
}
```

```go
// writeNameNode writes a NameNode inline in the BinXML stream and records its
// chunk-relative offset in refs.
//
// Layout: [next_offset: 4B = 0] [hash: 2B] [char_count: 2B] [UTF-16LE chars] [null: 2B]
//
// next_offset is written as 0 here. fillHashTables patches it later for the
// nodes it chains into a bucket; nodes it does not chain keep the 0.
func writeNameNode(b *bytes.Buffer, name string, binXMLBase uint32, refs *[]chunkRef) {
	h := sdbmHash(name)
	*refs = append(*refs, chunkRef{key: h, offset: binXMLBase + uint32(b.Len())})

	u16 := utf16.Encode([]rune(name))
	writeUint32LE(b, 0)             // next_offset, patched by fillHashTables
	writeUint16LE(b, uint16(h))     // SDBM hash
	writeUint16LE(b, uint16(len(u16))) // string_length
	for _, c := range u16 {
		writeUint16LE(b, c)
	}
	writeUint16LE(b, 0) // null terminator
}
```

- [ ] **Step 3: Implement `fillHashTables`**

Append to `chunkhash.go`:

```go
// fillHashTables populates a chunk's common-string and template offset arrays
// from the nodes emitted into that chunk, and patches the next_offset chains.
//
// Registration rule: the FIRST node with a given key wins its bucket. Later
// nodes carrying the same key are left unregistered and unchained — each record
// references its own inline copy through its own name_offset field, so a
// duplicate is already reachable, and chaining duplicates would make a table
// lookup walk an arbitrarily long run of identical names.
//
// Distinct keys that collide on a bucket DO chain, in emission order. That is
// ordinary hash-table chaining and is what a parser expects to walk.
//
// chunk must be a full evtxChunkSize buffer with the nodes already copied in at
// the offsets the refs name. MUST be called before patchChunkCRC: the chunk
// header checksum covers chunk[128:512], which is exactly what this writes.
func fillHashTables(chunk []byte, names, templates []chunkRef) {
	fillOneTable(chunk, stringTableStart, numStringBuckets, names)
	fillOneTable(chunk, templateTableStart, numTemplateBuckets, templates)
}

func fillOneTable(chunk []byte, tableStart, buckets int, refs []chunkRef) {
	// seen maps a key to the offset already registered for it, so duplicates
	// are dropped. tail maps a bucket to the last node in its chain, so a new
	// distinct key is appended rather than replacing the head.
	seen := make(map[uint32]uint32, len(refs))
	tail := make(map[int]uint32, buckets)

	for _, ref := range refs {
		if ref.offset == 0 || int(ref.offset)+4 > len(chunk) {
			// A zero offset is not addressable (0 means "empty bucket") and an
			// out-of-range one would corrupt the chunk. Neither can happen for
			// nodes the encoder emitted; skip defensively rather than panic in
			// a writer that is holding the caller's audit data.
			continue
		}
		if _, dup := seen[ref.key]; dup {
			continue
		}
		seen[ref.key] = ref.offset

		// Reduce in uint32 before converting. int(ref.key) would be negative
		// for keys above 2^31 on a 32-bit platform, and a negative modulus
		// yields a negative bucket index — an out-of-range write in a writer
		// that is holding the caller's audit data.
		b := int(ref.key % uint32(buckets))
		if prev, ok := tail[b]; ok {
			binary.LittleEndian.PutUint32(chunk[prev:], ref.offset) // chain onto the tail
		} else {
			putBucket(chunk, tableStart, b, ref.offset) // first node: becomes the head
		}
		tail[b] = ref.offset
		binary.LittleEndian.PutUint32(chunk[ref.offset:], 0) // terminate the chain here
	}
}
```

```go
func wrapEventRecord(recordID uint64, timestamp uint64, binXMLPayload []byte) []byte {
	// EVTX records are 8-byte aligned. The padding goes between the end of the
	// BinXML payload and the trailing size copy — never inside the payload,
	// which is a token stream where stray zero bytes decode as invalid tokens.
	unpadded := evtxRecordHeaderSize + len(binXMLPayload) + 4
	size := uint32((unpadded + 7) &^ 7)
	buf := make([]byte, size)

	binary.LittleEndian.PutUint32(buf[0:], evtxRecordSignature) // Signature
	binary.LittleEndian.PutUint32(buf[4:], size)                // Size, padded
	binary.LittleEndian.PutUint64(buf[8:], recordID)            // EventRecordID
	binary.LittleEndian.PutUint64(buf[16:], timestamp)          // TimeCreated (FILETIME)
	copy(buf[24:], binXMLPayload)                               // BinXML payload
	// buf[24+len(payload) : size-4] stays zero — the alignment padding.
	binary.LittleEndian.PutUint32(buf[size-4:], size) // Size copy at end

	return buf
}
```

## What the baseline actually said

Task 1 ran and recorded its result in `docs/format-baseline.md`. Two things came
out of it that were not known when the rest of this plan was written.

**F8, new: the `<Event>` root carries no `xmlns`.** Real Windows output always
declares `xmlns="http://schemas.microsoft.com/win/2004/08/events/event"` on the
root element — the vendored `system.evtx` contains that string 45 times, once
per template. go-evtx never emits it: `binxml.go` has no `xmlns` anywhere, and
`writeOpenElement("Event", false, baseOffset)` writes the root with no
attributes. This is a sixth format defect, in none of F1–F7, and it needs a
task of its own.

**But it is almost certainly not what breaks Event Viewer.** `Get-WinEvent`
throws `The event log file is corrupted.` on the call itself, before returning
any events — that is an **open-time** rejection, and at open time the parser has
read the file header and the chunk headers and nothing else. The `xmlns` lives
inside each record's BinXML, which is only reached after the file opens. Fixing
F8 should be expected to change the python-evtx `ObjectName` result and to leave
`Get-WinEvent` saying exactly what it says today.

**What the baseline eliminates.** The Linux job verified every chunk header CRC
and every chunk data CRC, and reported no mismatches. So the open-time rejection
is not a checksum failure — it is a structural or semantic one. That points at
the fields a parser reads before touching records:

| Read at open | Defect | Task |
|---|---|---|
| Chunk header `[128:512]` | Both hash tables all zeros (F1) | 5 |
| Chunk header `[44:]` | `LastEventRecordDataOffset` duplicates free space (F3) | 7 |
| File header `[120:124]` | Flags never written (F4) | 7 |
| File header `[16:24]` | `LastChunkNumber` underflow (F5) | 7 |

Two of those four are in Task 3, which is a few lines of header arithmetic, and
one is in Task 6, which needs the three-task interning chain behind it. Trying
the cheap ones first and re-running the harness is the fastest way to find out
which matters — see the ordering note below.

## Known risks, recorded up front

- **The bucket rule could be wrong.** Task 2 settles it against a real Windows file before any writer code changes, and stops the plan if it fails. This is the single largest risk and it is front-loaded deliberately.
- **`WriteRaw` chunks keep empty tables.** Caller-supplied BinXML is opaque, so its NameNodes cannot be registered. A `WriteRaw`-only session produces exactly what v0.6.0 produced. Document it in the `WriteRaw` godoc; do not pretend otherwise.
- **Registering only first occurrences is a judgement call.** Windows dedupes names per chunk and has later records reference the existing node; go-evtx keeps per-record inline copies and registers only the first. The tables end up correct and complete, but the chunk carries redundant NameNode copies. If the `Get-WinEvent` job rejects the file and the table walk itself checks out, true per-chunk interning is the next thing to try — a larger change, since it makes record bytes depend on what earlier records in the chunk already emitted.
- **`maxRecordPayload` shrinking by 7 bytes is a behaviour change** for callers writing records within 7 bytes of the old ceiling. Called out in the CHANGELOG.
- **The Windows job may simply fail.** That is an acceptable outcome for the release; keeping an unproven claim is not.

- `binformat.go:37` uses `t.UTC().UnixNano()` for FILETIME, undefined outside ~[1678, 2262], while `parseTimeCreated` accepts any RFC3339Nano year. Validate the range at parse time.
- `reader.go:81` rejects a valid zero-chunk file.
- The Reader validates no checksums, so it cannot classify corruption — it aborts.
- Embedded NUL in a field round-trips correctly but produces XML that is not well-formed under XML 1.0.
- `encodeUTF16LE` (`binformat.go:53`) is referenced only by its own test.
