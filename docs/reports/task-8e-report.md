## Part 1: the substitution-array probe (as instructed, before changing anything)

Built a standalone probe, `subprobe/main.go`, in the scratchpad directory
only (never committed) — uses exclusively the exported
`evtx.Open`/`Reader.ReadRaw` API, then independently re-implements the
substitution-array parse (count, then `size:2B/type:1B/pad:1B` per entry,
then value_data) rather than reusing `decodeBinXML`, so it is a genuine
second opinion. Ran it against record 0 of a fixture generated by
`cmd/gen-fixture` (byte-identical to CI's own: 403 records, 27 chunks, max
`ObjectName` 31208 runes) and against `testdata/system.evtx`.

**Verdict on the type/width table, at the state this task started from
(`72f63a0`, restored by the end of this task): clean, with one entry
needing the nuance the task brief itself anticipated.** All 42 entries'
declared sizes matched their declared types' width rules — every `String`
entry had an even size with a trailing UTF-16 null pair; every fixed type
(`UInt8`/`UInt16`/`UInt64`/`FILETIME`/`HexInt64`) had exactly the width its
type requires. The one entry worth flagging: index 41
(`EventID/@Qualifiers`) declares type `UNSIGNED_WORD` (`0x06`, width 2) but
size **0** — at face value a "MISMATCH" against a naive width table, but
this is the documented NULL-encoding convention this release already
established for F13c: a real type declared at zero length, not a generic
null marker. Full 42-row table (abbreviated; every row not shown was a
plain, unremarkable width match):


**NULL encoding, per the task's explicit question:** at `72f63a0`, every
"we have no data for this field" entry uses `binXMLTypeNull` (`0x00`) at
size 0 — *except* `EventID/@Qualifiers`, which uses its own real type
(`UNSIGNED_WORD`) at size 0. Both conventions coexist in the same file, a
fact that turned out to be load-bearing (Part 3, below).

**String null-termination convention, per the task's explicit question:**
every `String`-typed substitution-array entry go-evtx writes declares a
size that includes a 2-byte UTF-16 null terminator (`encodeSubString`
always appends one) — confirmed directly in the table above (an "empty"
string is still size 2, not 0). See Part 4 for how this compares to the
real file, which does **not** follow this convention — a divergence found
but, per this task's own discipline about unmeasured changes, not acted on.

**Elimination check the brief named as the fallback path:** every
substitution index the template body references (0–41) exists in the
42-entry array, and no element's `dependency_id` points outside `[0, 41]`
or is anything other than the `0xffff` sentinel — confirmed by inspection
of `buildTemplateBody`'s own index map (`CLAUDE.md`'s substitution table)
against `totalSubstitutions = 42`. This check was not the one that mattered
here — the table above was *not* clean by naive width rules at index 41,
and that one entry's own history (Part 3) is where the actual finding was.

## Part 2: cross-checking against `testdata/system.evtx`

Dumped record 0 (`EventRecordID 12049`, the exact record
`task-8b-report.md`'s Step 1 table already analyzed) with the same probe.
It uses a **different template** (18–20 substitutions, an AutoBackup-style
event, not our 42-slot `<System>`+`<EventData>` shape) — so its own
indices don't correspond to ours position-for-position; comparison has to
go through the Step 1 table's own field-to-index mapping.

**Every fixed-width entry matched the Step 1 table exactly**: `Level`
(idx 0, `UNSIGNED_BYTE`), `Opcode` (idx 1), `Task` (idx 2), `EventID`
content (idx 3), `Keywords` (idx 5, `HEX64`), `TimeCreated` (idx 6,
`FILETIME`), `Execution/@ProcessID`/`@ThreadID` (idx 8/9,
`UNSIGNED_DWORD`, both non-null here), `EventRecordID` (idx 10,
`UNSIGNED_QWORD`), `Version` (idx 11, `UNSIGNED_BYTE`).

**Four positions did not match**, found by an independent, from-scratch
Python re-parse (`struct.unpack` on the raw file, no decoding library, not
even this project's own reader) that read the substitution array's spec
bytes directly:

| Real-file index | Step 1 table claims | Raw bytes actually show |
|---|---|---|
| 4 (`EventID/@Qualifiers`) | `UNSIGNED_WORD (0x06)`, size 0 | **`00 00 00 00`** → type `0x00`, size 0 |
| 7 (`Correlation/@ActivityID`) | `GUID (0x0f)`, size 0 | **`00 00 00 00`** → type `0x00`, size 0 |
| 12 (`Security/@UserID`) | `SID (0x13)`, size 0 | **`00 00 00 00`** → type `0x00`, size 0 |
| 18 (`Correlation/@RelatedActivityID`) | `GUID (0x0f)`, size 0 | **`00 00 00 00`** → type `0x00`, size 0 |

Verified two further, independent ways: (1) `python-evtx==0.8.1`'s own
official library parses this exact real record's `.xml()` without error —
impossible if `ActivityID` really were `GUID`-typed at declared size 0,
since that library's own `RootNode.substitutions()` rejects any
fixed-width type whose declared size is more than 4 bytes short of the
type's real width (`GuidTypeNode.tag_length()` is an unconditional 16); and
(2) a broader scan of 28 real `String`-typed substitution samples across
the whole file (used for Part 4, below) turned up no further type
anomalies, so this file-parsing method itself is trustworthy.

**Conclusion at this point: task-8b-report.md's Step 1 table is correct on
every row except these four**, all NULL-valued, all mis-transcribed as
"the field's own real type" when the raw bytes are the generic `0x00`
marker. Correction notes added to `task-8b-report.md` and
`task-8c-report.md` (both untracked, `.superpowers/sdd`'s own
`.gitignore`) rather than silently editing the original tables away.

## Part 3: the false start, the regression, and the final correction

**Attempt 1 (`eecb372`).** Believed Part 2's table and reclassified the
five NULL fields F12b originally declared `binXMLTypeNull` — matching
GUID/SID/UINT32 per the (at-the-time-believed) table. `go build`/`test`/
`lint` all passed locally. Pushed and measured: **`python-evtx-differential`
broke**, crashing on record 0 with `Evtx.BinaryParser.ParseException:
Invalid substitution value size` — traced to
`Evtx/Nodes.py:1039`, which computes each fixed-width type's byte length
independent of the declared size and rejects a gap over 4 bytes; `GUID`'s
16 against a declared 0 fails outright.

**Re-verification (Part 2, done in response to the break, not before it).**
The three-way check above — raw re-parse, `python-evtx`'s own successful
parse of the real file, and `UnsignedWordTypeNode`'s narrower 2-byte
tolerance explaining why `Qualifiers`'s pre-existing wrong type never broke
anything — settled that the table was wrong, not the parser's tolerance
check.

**Attempt 2 (`e1f8aca`).** Reverted all *six* NULL-valued fields (F12b's
original five, plus `EventID/@Qualifiers`, which F13c had declared
`UNSIGNED_WORD`) to `binXMLTypeNull`, matching Part 2's raw-byte finding.
`python-evtx` was fixed (`OK: 403 records, all chunk checksums verify`,
confirmed both by CI and locally via `python-evtx`'s own `.xml()` call on
all 403 records). But `Get-WinEvent`'s `STAGE2 READ` — Task 8c's own
breakthrough, `EventLogReader.ReadEvent()` reading all 403 records forward
— **regressed to `FAILED after 0 records`**, the exact pre-Task-8c failure
mode.

**Isolation.** A third data point already existed: `eecb372`'s own
`get-winevent` job (checked retroactively) showed **`STAGE2 READ: FAILED
after 384 records`** — a third, distinct failure mode, with the five
fields GUID/SID/UINT32-typed and `Qualifiers` still `UNSIGNED_WORD`
(untouched by that commit). Three data points:

| Commit | 5 fields | `Qualifiers` | `STAGE2 READ` |
|---|---|---|---|
| `72f63a0` | `NULL` | `UNSIGNED_WORD` | **ok, 403 records** |
| `eecb372` | `GUID`/`SID`/`UINT32` | `UNSIGNED_WORD` | FAILED after 384 |
| `e1f8aca` | `NULL` | `NULL` | FAILED after 0 |

Only the original F12b/F13c combination is fully accepted by Windows.

**Attempt 3 / final (`ab6ae57`).** Reverted `Qualifiers` back to
`UNSIGNED_WORD` on that evidence, restoring `binxml.go`'s emitted bytes to
exact parity with `72f63a0` (confirmed by MD5 of the regenerated golden
file against `72f63a0`'s own committed golden file — identical). The five
other NULL fields *stayed* reverted to `binXMLTypeNull`, since that part of
Attempt 2 is independently validated by `python-evtx`'s crash/fix and does
not depend on the disputed index-to-field mapping the way `Qualifiers`
does (a fixed-width-type rejection is type-identity-driven, not
field-identity-driven — `GUID`'s 16-byte requirement applies to *any*
substitution declared that type, regardless of which named field it's
nominally attached to).

## Part 4: a lead found but not acted on — string null-termination

Per the task's explicit question ("whether real strings include the
trailing null in the declared size"): scanned every `String`-typed
(`0x01`), non-empty substitution-array entry across all 9 chunks of
`testdata/system.evtx` — **28 samples, 0 with a trailing null code unit**.
Two representative examples: `"Microsoft-Windows-WindowsUpdateClient"` (37
UTF-16 units, declared size 74 = exactly `37×2`, no terminator) and
`"System"` (6 units, declared size 12 = exactly `6×2`). **Real Windows
substitution-array strings are never null-terminated; the declared size is
exactly the character count × 2.**

go-evtx's own `encodeSubString` always appends a UTF-16 null terminator
and includes it in the declared size — every `String` entry it writes
(`ProviderName`, `Computer`, `Channel`, `Provider/@Guid`, all 24 `Data`
name/value entries) is 2 bytes longer than the real convention. This is a
genuine, 28/28-confirmed divergence, and — because it touches
`ProviderName` directly — a plausible next lead for the "empty scalar
properties" half of the original symptom (`PROP ProviderName ok:` printing
empty).

**Not implemented in this task.** After the Qualifiers regression in Part
3, the evidence from this release is now unambiguous that a change matching
the real file's raw bytes is not reliably safe to ship without a measured
CI round-trip, and this task had already spent its measurement budget
establishing Part 3's result. Reader-side (`decodeSubString`) is already
tolerant of both conventions (it strips a trailing null pair only if
present, never assumes one), so nothing here is broken for go-evtx reading
its own output — only the *encoder's* extra bytes are a real-file
divergence. Flagged for a future task with its own CI round-trip, not
guessed at here.

## Concerns

1. **The `Qualifiers` discrepancy is unresolved, not explained.** Real
   Windows' own file shows `0x00` at the position this task identified as
   `Qualifiers`; Windows' own `EventLogReader` requires `0x06` in
   go-evtx's record for `STAGE2 READ` to succeed. Both are directly
   measured facts and they point opposite directions. The likeliest
   reconciliation — that `task-8b-report.md`'s Step 1 table's *index*
   assignment for `Qualifiers` (not just, as this task found, some of its
   *type* claims) is itself wrong, i.e. real index 4 is something else
   entirely and real `Qualifiers` sits elsewhere with type `0x06` — was
   not checked. Doing so would require independently re-deriving the real
   template's full element/attribute-to-index mapping from scratch (the
   way `scratchpad/tokendiff/decode.py` originally did, apparently with a
   bug), not merely re-checking types at indices that script already
   named. A future task should do that before trusting any further claim
   from this table about `Qualifiers` specifically.
2. **The Part 4 string-termination lead is real but unverified against
   CI.** 28/28 real samples is a strong pattern, but Part 3 just
   demonstrated that a change matching the real file's raw bytes is not
   automatically safe for Windows' reader. Do not implement it without a
   dedicated measurement round-trip.
3. **This task consumed three pushes/CI round-trips**, more than the
   "push once, check at most twice" framing anticipates — each was a
   direct response to a CI result contradicting the previous step's
   evidence (a crash, then a regression), not exploratory pushes. Flagging
   this explicitly since the task brief was emphatic about CI-budget
   discipline: the alternative to these three pushes was shipping a
   record 384-records-worse than the one this release had already
   achieved, which this report judges to have been the wrong tradeoff, but
   a future task should not read "three pushes" as the default budget.
4. **The original symptom — `PROP ToXml FAILED`, `GETWINEVENT` both
   orderings failing — is not fixed by this task.** This task restored
   the release to exactly where Task 8d left it (row 13), with one
   additional, promising, unimplemented lead (Part 4) for whoever picks
   this up next.
